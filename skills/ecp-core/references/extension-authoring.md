# Extension and plugin authoring (ECP core)

Every extension follows third-party rules. Full contract: `.cursor/rules/extensions.mdc`.

## The definition (stable across the reset)

1. `defineExtension(ns, name).withMetadata(...).withCapabilities([...]).build()`
2. Capabilities via `capabilityFor(id, name).withInput(...).withOutput(...).withMetadata(...).withHandler(...)`
3. Metadata is product prose with at least one `useCases` and one `projections` entry.
4. zod schemas, imported from `"zod"`.

## What changes in the reset

| Concern | Now | After |
| --- | --- | --- |
| Registration | Export the definition; bind `extension(def)`. Hosts call `registry.registerExtension(definition)` | Phase 5: remaining packages move; `ecp plugins build` already generates CLI files |
| Where it runs | `.supports(environmentId, range?)` | Unchanged after Phase 2 |
| Package | Model plugins and jsonata live in `plugins/plugin-*`. Remaining extensions are in `packages/extensions` or `packages/vendor` | Phase 5: remaining `plugins/plugin-<extension name>` |
| CLI commands | None | Generated by `ecp plugins build`; nothing hand-written |

## Dependencies

| May use | Must not use |
| --- | --- |
| `core` (including `core/types`), `zod`, focused libraries, `plugin-sdk` (from Phase 3) | `node`, `browser`, `cli`, `mcp` |

## Test

- Use fixtures and `environment()` from core, not host packages, inside extension tests.
- From Phase 5, each plugin also has a CLI-level `--json` test and passes `ecp plugins check`.

Vendor extensions live in this monorepo (`packages/vendor` today, `plugins/` after Phase 5). The
old separate `executioncontrolprotocol/extensions` repo is archived.
